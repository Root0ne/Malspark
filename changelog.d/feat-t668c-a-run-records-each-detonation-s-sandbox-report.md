### Added

- **A finished run records each detonation's sandbox run (T-668).** The run summary's `environment` block gains `detonations`: one row for the job's own detonation and one for each further detonation an agent asked for, saying which it is, whether the job or the agents named asked for it, the launch text it asked for, exactly, with whether the provider passed it and how, the sandbox provider, the task id, and whether a report came back or why not. Beside these, each row holds what the provider states of the sandbox run, read while the report is in hand: the provider's identifiers of the analysis, the guest as the report names it (a CAPE or Cuckoo report's analysis machine, each Triage behavioural task's target), the sandbox's version, the start and the end where the report gives them, whether the sample was run (not for a report the mock sandbox replays or an operator attaches), and the SHA-256 and byte length of each raw report part as it was read — CAPE's report, Triage's overview and each task report, the REST provider's report body, the attached report's bytes, or the fixture file the mock sandbox replayed — so two runs can be shown to rest on the same sandbox report or on different ones. A detonation that returned no report lists no part. Every provider is asked through one method, `SandboxProvider.detonation_facts`; a provider that does not implement it, a plug-in among them, states nothing, and each fact it would have stated reads "not reported". What a provider or its sandbox wrote is kept to the known keys, capped, put on one line, and holds no credential, secret value or path of the worker's host; task URLs are not recorded. A job that asked no sandbox for anything records an empty list. The block's shape version is 3.
