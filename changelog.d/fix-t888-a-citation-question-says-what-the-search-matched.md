### Fixed

- **A citation question says of each entry what the search matched there, and a cited entry holds a value its text writes as bytes (T-888).** Where the citation check asks about a value cited to an entry that does not hold it, it says "found whole in" an offered entry only where no letter, digit or `_` of the run the value stands in, read decoded, touches the value; of every other entry it says that the value stands there only inside a longer run of text, where the search matched it (between which characters, or at the start or the end of the run) and the run, or that the run is not shown. In a question about several values each value is worded for itself, and the mark printed beside a kept citation says the same. The same entries are offered and the same questions asked. In the check's test of the cited entry alone, the entry also holds a value its text writes as bytes — a token of hex pairs, a JSON array of numbers 0–255 or a run of `\xNN` escapes at a byte-escape level, decoded as UTF-8 or UTF-16LE and holding the value whole — where the chance of that among the entry's byte runs, over the symbols each token is written with, is under the platform's one chance bound. A run the entry's own call wrote, or its echo, holds nothing: a run the call's arguments write as bytes, and a run equal to the UTF-8 or UTF-16LE bytes of one of its string arguments, as written or lower-cased (a longer run holding them is data); a run's end bounds a value only where it ends its JSON string or array, or the text, a split between a list's rows at any depth bounding nothing. The question names the byte reading where it read a place, and never says a value is absent; where a cited entry's bytes write the value whole and only the chance bound refuses the holding, the question and the mark beside the citation say that the bytes hold it and why that is not counted.
