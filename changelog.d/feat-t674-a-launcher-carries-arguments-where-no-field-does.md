### Added

- **A launcher carries a job's launch arguments where the sandbox has no field for them (T-674).** A provider may declare that it honours launch arguments through a generated launcher (`SandboxCapabilities.launcher`: the script types it runs and how its submission names the one to run). The platform builds, once, a deterministic archive of the sample as `sample.exe` and a PowerShell launcher that finds its own folder from the path it was started from (from PowerShell 2.0 on; the current location where its content is run with no script path) and starts the sample there through `System.Diagnostics.Process`, not the shell and with no wildcard reading of the path, with that folder as its working directory and the arguments as one string exactly as the job gave them, and the provider submits that archive. Triage uses it, picking the launcher with `profiles[].pick`; `sandbox.triage.launcher_for_arguments` (default on) turns it off, and the request is then recorded as not honoured as before. Only a Windows program (not a DLL) is launched this way; a DLL, a script and an installer stay refused with the reason, and a batch launcher is not built (`%`, `^`, `&` and non-ASCII are unsafe in one). The launch record, the upload record, the ledger's sandbox entry and the report give the launcher's exact text, its member names and the SHA-256 of the archive, of the launcher file and of the sample, and state that the process tree starts at the script host, that the archive is what the sandbox received (public on a public sandbox), and that nothing shows the launcher ran. The disclosure counts the archive as what left the machine, also when the submission failed. The report is read with the launch record's generated names, each process by its task and its id: the script host running the launcher is the launcher's, not the sample's, the sample's tree is rooted at `sample.exe`, a flow of the launcher is marked as its, a signature seen only in the launcher in every task is moved, marked, to a `launcher.signatures` channel and kept out of the sample's techniques (one naming no process takes its processes from the task's signature of that name, and one that still names none is counted as attributed to no one), the archive's members among the written files are marked as the platform's, the sandbox's score and family are stated to judge the archive and the family carries that note, and the archive's SHA-256 as the sandbox's target is the submitted archive, not another target. Where no listed process runs `sample.exe`, only the script host is the launcher's, what it started is attributed to no one, and the report's `launcher_attribution` mark says the attribution was not established. The lineage is held under the platform's own `platform_lineage` key, taken out of a report at intake wherever a sandbox's field carries it.

### Changed

- **Every process and flow row of a sandbox that reports tasks carries its task (T-674).** A Triage report's process and flow rows now carry `platform_task` and `task`, whether or not the job asked for launch arguments, and the process view states each process's task. Stored runs are unaffected.
- **A plug-in provider's one-argument `launch_arguments_answer` is called with the arguments alone, and CAPE no longer withholds the arguments for a package the documentation is silent on (T-670).** The package is still sent them and the record notes that whether it reads them is not documented. A refused value is named by code point and position, an over-long refused value is recorded with a note that it was cut, and a submission that sent the arguments but returned no report is worded "sent ... but no sandbox report came back" in the limitations and the upload line alike.

### Security

- **A sandbox's failure text is searched for the job's launch arguments and the launcher text before it is logged or kept (T-670, T-674).** In an exception's message or a response body of a submission, the submitted values are withheld where they occur as sent, JSON-escaped or in any percent-encoding (either case of hex digit, a space also as `+`), only the stretch that decodes to them being replaced; other encodings (base64, a changed case, a cut copy) are not recognised. The platform's own words around that text are not masked, and a value shorter than four characters is not masked at all, so it may appear in a sandbox's failure text the platform logs or keeps, which the launch record says. "Sent" is said only once the provider's submit call returned.
