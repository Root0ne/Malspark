### Added

- **A finished run records the environment it ran in (T-668).** The run summary carries an `environment` block, wherever the summary is stored, served and exported: the worker's host (operating system and release, machine type, processor model, and the kernel's logical processors and total memory, with the processors and memory limit the worker process itself may use where its control groups say), and per agent one row for each model it was built to send with — the configured model, a path-shaped one kept by its base name; the sampling parameters and thinking switches its provider adapter read off the request body the client built when the model was built, the statement that none was sent and the provider's default applied, or "not reported"; how many requests the platform changed a thinking switch of after that; the effort level with the setting it came from, or why none was sent; and how many recorded answers came from that place in the list, so a fallback that was never needed reads 0 — beside each model identifier the provider's answers named, a path-shaped one kept by its base name. The block also records the tools the run ran: one row per tool server the job attached, its own or one a provider attached itself, saying whether its tools were offered to an agent, called by one, run by a triage pack step or only attached, with the name and version the server gave when attached, its manifest's version (the platform's own version for the platform's servers, the program's pinned version for a server that wraps one command-line program), and what each requirement its tools declare was on its host when its capability manifest was read — a library's installed distribution and version, a rule set's file count and one SHA-256 over the files its loader reads, and a program's version where its tool declares how to ask it (the string-extraction tool's pinned build, and `ilspycmd`, `jadx` and `yr` in their sidecars; the other command-line sidecars give the version their image pins). The pack steps the worker runs itself have a row of their own, read with the environment of the server each stands in for. Every answer of a tool that matches rules starts with the rule set the call ran with, the one its arguments named or else the default, with its file count and digest at that moment, so the ledger entry of each such call names its rules. A server that answers no capability manifest (most third-party servers, and the disassembler and decompiler servers the static providers attach) gives its name and version only, the sandbox providers report no server yet, and what a third-party manifest says is reduced to the known keys and capped before it is stored. Each fact appears only where it was read, and one that was not is "not reported", never a statement that nothing was sent; a summary stored without the block reads as before. A caller that publishes a run summary with benchmark evidence can sanitise it so that its model identifiers are left by the host and run-name rules and pass every other rule; the benchmark evidence published today carries no run summary.

### Fixed

- **The model build log line states the sampling actually sent (T-668).** It used to print the temperature handed to the provider, which a model whose API or client library drops sampling parameters is never sent. The line now names the sampling read off the request body the client would send.
