### Fixed

- **A Sigma selection that can match alone holds a specific value, and a Sigma draft carries only the techniques that name what it selects (T-714).** Each selection of a Sigma draft can match alone, so `detection_signatures.selection_specific` takes out every value the benign-location catalogue calls every Windows host's (`benign_reason`, asked of the value as printed, a sandbox-recorded key or image included, with a reason true of the value as stated) and every `contains` value another selected value lies under or that is a longer spelling of another (the folder a selected file lies in), case and separators folded; a selection left empty is taken out, and a draft left with none is not built, its reason printed in the existing "No Sigma draft" line. Each value taken out of a draft that is built is kept on the rule's record (`values_left_out`), not printed. The builder and `drafts_not_built` read the one decision. A write a sandbox recorded under a key every installation has is selected by the key with the value's name and what its data names: `sandbox_registry_ops` reads the value's name a write call carries (`ValueName`, `lpValueName`) into its row's new `value_name`, which fills `RegistryMod.value_name`, and a row is a key and the value an operation names, with its own operation and pids (an operation naming no value is the key's own row, a delete of one value only that value's). Every program and file path the data of a persistence payload or a written value names is read by the rule drafter's own reading (`detection_signatures.data_words`, over `sandbox_report.command_line_paths`, now public, a quoted path read whole; the sandbox's check of which process runs the submitted file reads a command line as before): a program of the sample's own is selected as the image in a process-creation draft and in the data (`Details`) in a registry-event draft, whose `Image` is the process that wrote the value; a program no data holds is left out of a registry-event draft with why; after a program Windows ships (also written under an environment name of the system root), each further path is selected in the field that records the data (`Details` in a registry event, `CommandLine` in a process creation); an unquoted program whose first word begins a rooted path and names no file is read with its words joined by their spaces up to the first that ends in a file name, the first word standing alone at a switch, at another rooted path, and where the words so far with `.exe` added end in a program Windows ships, and a further name with no folder is never selected; only a write names a program. Last, every printed value is asked the way the rule matches it (`stated_host_values.shipped_match`, the paths Windows ships derived from the catalogue's program names, system roots and system folders, and its keys): a value a shipped path ends with (`endswith`), holds (`contains`) or is, is never selected, with a reason that says so. A path whose cut form is a file name Windows ships keeps its folders past the drive and the user's own name (`Users\Public` kept), a long-path prefix is read off, and a path printed as such a name alone is never selected, with a reason that says so. A Sigma draft is tagged with a technique only where the technique's evidence quotes or roots name a selected value whole and delimited (quoted, in code marks, or as a path component), with a tactic only for a technique kept, and with no `tags` key when none is. The registry tool's answer gains `value_name` on the row of a write or delete that names a value, and a row for each value an operation names on the same key, paged and sized like every sandbox view; no other text a model reads changed. The YARA and Suricata drafts are unchanged.
