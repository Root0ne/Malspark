### Added

- **An agent may ask for a further detonation with launch arguments it found (T-671).** Where the job's sandbox can pass launch arguments, the in-process sandbox source holds `request_detonation(arguments, reason, cited_entries)`. It records the request and answers in code: accepted as `d2`, `d3`…, joined to an identical pending request (one detonation, every asker named), or refused with the reason (not one command line, no reason, cited entries the run had not issued, a sandbox that cannot detonate or pass the arguments, the ceiling, an identical detonation already made, or no later step that reads the sandbox). Accepted requests are carried out on entry of the next step that has an agent reading the sandbox, through the job's own submission path, with no new graph node; each records its step, start, end and duration and is announced with `detonation_started` and `detonation_finished`. On the debate's first negotiation entry, each analyst that reads the sandbox and ran before a detonation returned gets one further turn (`further_turn_started`, `further_turn_finished`). The sandbox readers take a `detonation` selector, a later detonation's item ids are qualified (`d2/proc:84`), the report draws each later detonation in tables titled with its launch and who asked (never merged into the job's own dynamic block; the composer is shown them apart), the disclosure lists each submission apart, the run summary lists the detonations, requests and further turns, and a request not carried out is a limitation of the run. New setting `core.sandbox.max_detonations_per_job` (default 4, the job's own detonation included), stated to the agents as the sandbox's limit.

### Changed

- **What changes for every run (T-671).** Every sandbox reader tool, and the network analyst's `sandbox_items`, has an optional `detonation` field in its schema and one sentence about it in its description; the shipped declarations' digest changes (the new `request_detonation` declaration); the settings snapshot gains `sandbox.max_detonations_per_job`; the item-id pattern reads a `d2/`…`d999/` qualifier. Where the job's sandbox can pass launch arguments, agents holding the sandbox source are offered `request_detonation`. A run in which no agent asks records, reports and summarises as before.

### Fixed

- **A family the sandbox named in a launcher run says, in the report, what the sandbox judged (T-671).** The rendered family line and the analyst report print `family_note` beside the sandbox as the family's source, and the console's report type carries the field.
