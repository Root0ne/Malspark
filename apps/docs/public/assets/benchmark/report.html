5.1 Packing, obfuscation and anti-analysis

No packer is present in the analysed sample. The PE reader reports an empty packer-signature list, and the packer scan matched no packer signature13. The packer scan's only matched rule is HasRichSignature at 0xb8, a Rich header that is a linker artefact, so its packed flag rests on no packing content36. The PE reader reports no overlay and no resources, and the carver found no embedded, split, bitmap-hidden or encrypted PE37. Section entropy is 5.42 (.text), 6.48 (.data), 4.68 (.rdata), 3.87 (.pdata) and 0.08 (.reloc)13. The highest value lies in .data, where the encoded string blobs sit; we assess that this reflects those blobs rather than a packed body38. No YARA rule of the 31 tested matched20.

The sample does obfuscate its text. Its strings are stored XOR-encoded in .data and decoded at run time by the routine at 0xae7838. The routine reads a 4-byte seed, then a 2-byte length XORed with the low 16 bits of the seed, then the encoded bytes. Byte i is XORed with the low byte of (seed + 1 + i). For the seed 0x33629d40 the first key is 0x41, so byte i uses 0x41 + i39. The blob at 0x10250 shows the layout: header 40 9d 62 33 5f 9d, length 0x9d5f XOR 0x9d40 = 31 bytes (30 characters and a NUL), and a one-step decode yields a URL40. The platform decoder recovered 101 blobs, and FLOSS emulation recovered 81 strings, 90 of the blobs also being recovered by FLOSS41. The decoded text includes command-line fragments, WMI and WinINet strings, registry and file paths, and the network values, which are given under command and control42. The decoder skips encoded text whose bytes already read as printable, so further encoded text may remain undecoded38. The plain-text run list yields 218 runs and the plain-text IOC scan returns no indicators, so the plain strings carry no network or host values43.

API names are hidden as well. The routine at 0x8690 reads the PEB through the GS segment at offset 0x6044, and the resolver at 0x869c parses PE export tables45. The platform's scan recovered 164 Windows function and module names from stored CRC32 values, across 10 hash algorithms46. The CRC-32 routine at 0x6aa4 uses the CRC-32 polynomial constant, and the FNV routine at 0xc99c uses the FNV-32 offset basis and prime47. The hashing structure is established; the individual name-to-hash mappings are recovered by scan and have moderate confidence until confirmed by emulation. Capa also reports obfuscated stack strings at 0x9484 and an RC4 PRGA routine at 0xcaac45. Capa's T1027 and T1027.005 labels are its rule metadata.

The analysed sample carries two evasion-relevant behaviours: obfuscation of its strings and API names, and self-deletion of its own image. The deterministic anti-debug API count is zero, and the Ghidra anti-analysis scan matched only a single PEB read (GS segment, offset 0x60) at 0x8690, which the capa rule also reports as PEB access48. The sample is not packed by any known signature and matched none of the 31 YARA rules run49. The analysed sample is therefore not shown to use anti-debug or environment checks.

Data obfuscation is the main evasion measure. Most strings are stored as XOR-encoded blobs with a rolling 8-bit key (seed 0x33629d40, first key 0x41, UTF-16LE or ASCII text) and are decoded at run time by routine 0xae78, whose body XORs each encoded byte with a key stream advanced per byte50. Emulation recovered 81 decoded strings and the platform decoded 101 blobs42. The capa rules report obfuscated stack strings at 0x9484, CRC-32 hashing at 0x6aa4, RC4 PRGA at 0xcaac and FNV hashing at 0xc99c52. Dynamic API resolution (T1027.007) is therefore the sample's main way of hiding its imports, since its import table lists only KERNEL32.dll and USER32.dll13.

The sample resolves most of its Windows API surface at run time rather than through its import table. The static import table holds five names from two libraries (KERNEL32: PeekNamedPipe, GetLastError, CreateMutexW; USER32: MessageBeep, MessageBoxA)13. The export table lists four names: extra, follower, run and scub69.

Routine 0x33ac first copies the module path, held in DAT_1360bc10448 and set through GetModuleFileNameW in 0x841c70, to a new file. The texts at 0xf9a0, 0xf9b0 and 0xf9d8 are not decoded in the analysed sample's string recovery, so their values are not stated here.

7. Conclusion

The sample is assessed as Malware (high confidence), a downloader / backdoor (Latrodectus-family implant), attributed to the family Latrodectus (moderate-to-high confidence)1, at high severity.

The sample is a 60,928-byte x64 Windows DLL, unsigned and submitted under an .exe name, that works as a downloader and backdoor; engine labels name Latrodectus most often, but the family is not confirmed8. Its code carries an encrypted HTTP beacon, a fetch-and-run path, logon-triggered scheduled-task persistence and host and domain discovery through cmd.exe, all recovered from XOR-encoded data that it decodes at run time93. Engine labels are mostly consistent with that reading, though some name IcedID, so the family attribution is moderate-to-high rather than certain19.

For a defender, the file should be treated as an active implant rather than a benign DLL. Any host that loaded or executed it should be isolated and investigated for a scheduled task named Updater, for the cmd.exe discovery commands and for outbound HTTP POST traffic to the two candidate C2 domains recovered from the decoded strings42. Blocking those domains at the perimeter is a reasonable precaution.

We assess with high confidence that the sample is malicious, because the verdict rests on 56 of 75 engines and on the decoded capability set143. Confidence in the Latrodectus attribution is moderate to high, and confidence that the implant behaves as its code suggests at run time is low, because the sandbox recorded no C2 contact and no dropped file, and its output carries no tasks section, so no task registration was observed144.145
