This page takes a clean checkout to a first finished analysis. It needs about
fifteen minutes and a model to talk to: a hosted API key, or a local server.
For a production install, read [Deployment](/docs/deployment/) afterwards.

## Before you start

- Docker with the Compose plugin: Docker Desktop on Windows and macOS (Linux
  containers, the default), Docker Engine on Linux
- [uv](https://astral.sh/uv/), which provides the Python the setup commands
  run on; they use the standard library only, so the host installs none of
  the project's dependencies
- `git`, and `curl` and `jq` for the API examples
- Free host ports for the services below. Every published port binds to
  `BIND_ADDRESS`, which is `127.0.0.1` by default.

The commands below are the same in PowerShell, on macOS and on Linux. Where
make is installed, each `malspark_dev.py` command also has a make target of
the same name (`make external`, `make dev-up`, ...).

**Supported systems.** Windows (native PowerShell with Docker Desktop), macOS
and Linux. In CI, the Platforms workflow runs `setup`, `setup --dev`,
`env init` and `doctor` from a fresh checkout on Ubuntu, macOS and Windows
runners, validates the compose files on Ubuntu, and runs the host-side unit
suites on Windows; these checks do not gate a merge.

<Steps>

<Step>

### Clone and fetch the third-party trees

```bash
git clone https://github.com/Root0ne/Malspark.git
cd Malspark
uv run --no-project python scripts/dev/malspark_dev.py setup
uv run --no-project python scripts/dev/malspark_dev.py doctor
```

`setup` fetches what is not kept in git: the tree the `ghidra-mcp` image is
built from, capa's rules and signatures (`data/capa-rules`,
`data/capa-signatures`) and the Sigma rule corpus (`data/sigma_rules`), each
at its pinned version and checked against its recorded digest. `doctor` says
what the host still lacks: Docker in Linux-containers mode, the Compose
plugin, free ports, the fetched trees. To work on the code, `setup --dev`
(`make setup`) also installs the Python dependencies and the pre-commit
hooks.

The stack mounts this checkout's `data/` over the image's copy, so run
`external` (`make external`) again in any new checkout or worktree. Without
the rule corpora a run still completes, but it is marked degraded and names
what was missing.

</Step>

<Step>

### Write the two configuration files

Malspark reads two files, and neither is committed.

```bash
uv run --no-project python scripts/dev/malspark_dev.py env init
```

**`docker/.env`** holds the values Compose substitutes into the stack.
`env init` writes it from `docker/.env.example` with a generated value for
each secret the example leaves empty (the infrastructure tokens and
passwords, `SETTINGS_ENCRYPTION_KEY`, `JWT_SECRET_KEY`). The core secrets
are declared with `:?` in the compose file, so the stack refuses to start
while one is missing.

**`bootstrap.env`** (repository root) holds the same contract as process
environment, for anything you run outside Compose, such as `make migrate`.
`env init` writes it with the same secrets and a `DATABASE_URL` on the port
the stack publishes Postgres on (5432, or your `POSTGRES_PORT`). `dev-up`
reads it too, and an empty value there would override `docker/.env`.

Neither file is overwritten once it exists, with one exception: when
`docker/.env` gets a new secret, the `bootstrap.env` values that carry it are
derived again, so the two never disagree. `env init --force` rewrites both
from the examples and keeps every value already set, empty ones included; it
fills only an empty secret, and replaces a `bootstrap.env` value only when it
is empty or still the example's placeholder. No secret is printed.

These two files are the whole environment surface. Every other setting lives
in the settings store and is edited in the console. See
[Configuration](/docs/configuration/#the-bootstrap-contract).

</Step>

<Step>

### Start the stack

```bash
uv run --no-project python scripts/dev/malspark_dev.py up     # make dev-up
uv run --no-project python scripts/dev/malspark_dev.py logs   # make dev-logs
```

The development overlay runs the console under `next dev` and restarts the
worker on a source edit. A compose file of your own (a port moved, a service
turned off) is added with `COMPOSE_FILE_EXTRA=docker/local.yml make dev-up`;
see [Your own compose overrides](/docs/development/#your-own-compose-overrides). For the production shape, run `make docker-up`
instead.

The one-shot `migrate` service applies the database migrations first. The API
and the worker wait for it.

| Service | Address |
| :-- | :-- |
| Console | `http://localhost:3000` |
| API health | `http://localhost:8000/health` |
| Ghidra MCP | `http://localhost:8089` |
| MinIO console | `http://localhost:9001` |

Ghidra and Qdrant run under the Compose profiles `ghidra` and `qdrant`, which
`docker/.env` turns on (`COMPOSE_PROFILES=ghidra,qdrant`). To run without one,
take its name out. Then pick another static analyser, and without Qdrant set
`core.memory.backend` to `memory`.

</Step>

<Step>

### Create the first account

Settings and the audit log need the `admin` role, and no endpoint grants it:
an account registered from the console's login page gets `analyst`. Make the
first admin from the command line, in the API container:

```bash
uv run --no-project python scripts/dev/malspark_dev.py create-admin you@example.com
# or: make create-admin EMAIL=you@example.com
```

It asks for the password twice, hidden, and creates the account with the
`admin` role. If you already registered that address from the console, it
promotes the account instead and asks for nothing; sign out and back in. See
[`malspark create-admin`](/docs/cli/#malspark-create-admin) for the options
and for a scripted run.

</Step>

<Step>

### Connect a model, a sandbox and the tools

A fresh stack starts on catalogue defaults, which point at `localhost` and so
are wrong inside the Docker network. Open **Settings → Setup guides** and walk the
guides you need:

- **Connect a language model.** Provider, endpoint and key. A local
  OpenAI-compatible server is reached from the containers at
  `http://host.docker.internal:8080/v1`. See [LLM providers](/docs/providers/).
- **Choose a static analyser.** For the bundled container, the Ghidra URL is
  `http://ghidra-mcp:8089` with your `GHIDRA_MCP_AUTH_TOKEN`.
- **Connect a sandbox.** CAPEv2, Hatching Triage, any REST sandbox, an uploaded
  report, or the mock sandbox, which is the default and executes nothing. See
  [Sandboxes](/docs/tools/sandboxes/).
- **Set up long-term memory.** Qdrant at `http://qdrant:6333` with your
  `QDRANT_API_KEY`.

Each guide includes a connection test. Malspark refuses a
job whose model has never answered a connection test, so run the test.

</Step>

<Step>

### Run your first analysis

Upload a sample in the console and press **Start analysis**. Or use the API:

```bash
API=http://localhost:8000/api/v1
TOKEN=$(curl -s -X POST $API/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"you@example.com","password":"..."}' | jq -r .access_token)

SAMPLE=$(curl -s -X POST $API/samples/upload \
  -H "Authorization: Bearer $TOKEN" -F 'file=@sample.exe' | jq -r .id)

JOB=$(curl -s -X POST $API/jobs -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{\"sample_id\":\"$SAMPLE\"}" | jq -r .id)
```

Follow the run on the analysis page. **Evidence → Analyst discussion** shows
every agent's messages and tool calls as they happen; **Evidence → Records**
is the ledger. When the job is `completed`, read the report:

```bash
curl -s $API/reports/job/$JOB -H "Authorization: Bearer $TOKEN" | jq -r .id
curl -s $API/reports/<report id>/markdown -H "Authorization: Bearer $TOKEN" > report.md
```

</Step>

</Steps>

## Read the report from the evidence up

Every report section carries the ledger ids it was built from. In the console
each id is a chip that opens the call under **Evidence → Records**, with its
arguments, its answer and its duration. **Evidence → Evidence bundle** prints
every section with the entries it cites. See
[The evidence ledger](/docs/concepts/ledger/).

## Next steps

- **Measure the model without tools.** The `measurement` team runs the same
  analysts with every tool withheld. Compare its report with the default run
  to see what the tools added. See [Agents and
  teams](/docs/usage/teams/#the-measurement-baseline).
- **Try another team.** `mobile` is built for APK and DEX files;
  `deep_static` adds a reversing stage that takes each static finding into the
  decompiler. Pick one per job with `{"config": {"profile": "mobile"}}`.
- **Add your own tools.** See [Bring your own tools](/docs/tools/).

## A smaller model for a smaller machine

On a machine that cannot hold a larger model, `gemma4:12b` behind Ollama
works with one required setting:

```
core.llm.provider                 = ollama
core.llm.ollama.expert_model      = gemma4:12b
core.llm.ollama.judge_model       = gemma4:12b
core.llm.ollama.disable_thinking  = true
core.llm.ollama.num_ctx           = 32768
```

Without `disable_thinking`, the model puts its whole answer into the thinking
channel, the connection test reports that it answered nothing, and every job
is refused. Expect fewer ATT&CK techniques than from a larger model.

## Without Docker

The [command line](/docs/cli/) runs the pipeline in one process, with no API,
worker or backing service:

```bash
uv run malspark analyze sample_1 --mock --name test.exe
```
